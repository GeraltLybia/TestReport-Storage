# TestReport Storage

Веб-приложение для хранения и просмотра тестовых отчетов Allure.

Это независимый продукт для хранения, просмотра и анализа тестовых отчетов, сгенерированных Allure Report, включая отчеты из экосистемы [allure-framework/allure3](https://github.com/allure-framework/allure3).

## Структура проекта
- `frontend` - приложение на Vue 3 (интерфейс управления и просмотр отчетов)
- `backend` - сервис на FastAPI (загрузка/скачивание/список/удаление отчетов, работа с history)
- `storage` - runtime-директория для отчетов и `history.jsonl`, находится в `.gitignore`


## Backend-структура
Внутренний backend-код для домена отчетов и history теперь лежит в пакете `app/services/reporting`.

Логика разделена по слоям:
- `app/services/reporting/reports.py` - сервис работы с отчетами
- `app/services/reporting/history.py` - сервис работы с `history.jsonl`
- `app/services/reporting/history_index.py` - построение и обновление `history_index.json`
- `app/services/reporting/analytics.py` - агрегаты для dashboard
- `app/services/reporting/runs.py` - прогоны, восстановленные из history index
- `app/services/coverage/` - измерение покрытия API: разбор log-вложений, сопоставление с OpenAPI и GraphQL-схемой
- `app/services/jira/` - баги в Jira: шаги и стенд из отчёта, разметка описания, клиент Jira, связи задач с падениями
- `app/services/reporting/repositories/` - файловые repository-слои
- `app/services/reporting/models.py` - внутренние typed-модели

Это сделано специально, чтобы не путать кодовый пакет с runtime-папкой `storage/`.

## Запуск через Docker
Образы собираются пайплайном CI/CD компании; Dockerfile не хранятся в этом репозитории.
Обе сборки используют корень репозитория как контекст:
- Backend: `COPY ./backend/ ./` — uvicorn на порту 8000, хранилище в `/app/storage` (`APP_STORAGE_ROOT`)
- Frontend: multi-stage `node:22` → `nginx` — UI на порту 80; `/api` и `/reports-static` проксируются на backend (при запуске UI и backend на разных хостах задаётся build-арг `VITE_API_BASE`)

Адреса в развёртывании:
- UI приложения: `http://localhost:9999`
- Backend (внутри docker-сети): `allure-storage-backend:8000`

## Основные возможности
Продуктовое описание со скриншотами — в [README.md](./README.md).

- Дашборд качества по истории прогонов: pass rate и риск, тренд прогонов, нестабильные тесты с полосой последних запусков, сигнатуры падений, состояние по тегам
- Фильтры дашборда по suite, environment, сигнатуре сбоя, периоду и тегам (с поиском по тегам); фильтры сохраняются в query-параметрах URL
- Панель деталей теста: последний статус, pass rate, длительность по прогонам, история запусков с ошибками
- Загрузка Allure-отчётов (`.zip`), список с поиском и фильтром по статусу, встроенный просмотр, скачивание и удаление
- Вкладка «Результаты тестов» у отчёта: упавшие и все тесты из данных самого Allure-отчёта
- Раздел «Прогоны»: прогоны, восстановленные из `history.jsonl`, постранично с сервера, с результатами тестов
- Покрытие API: REST по OpenAPI/Swagger и GraphQL по схеме (SDL или интроспекция) на основе log-вложений тестов; граф схемы в стиле GraphQL Voyager
- Баги в Jira из упавших тестов отчёта: шаги, запросы, стенд, автор, логи; связь задачи с падением и поиск дублей (см. [Интеграция с Jira](#интеграция-с-jira))
- Загрузка/скачивание `history.jsonl`, инкрементальное обновление индекса истории
- Светлая и тёмная темы
- Автоматическая ротация отчётов по лимиту (по умолчанию храним 10 последних)
- Healthcheck endpoint: `GET /health`

## Reports API
- `GET /api/reports` - получить список загруженных Allure-отчетов с метаданными
- `POST /api/reports/upload` - загрузить новый Allure-отчет в виде `ZIP`-архива (`multipart/form-data`, поле `file`)
- `GET /api/reports/{report_id}/download` - скачать конкретный отчет как `ZIP`-архив
- `DELETE /api/reports/{report_id}` - удалить отчет по его идентификатору
- `GET /api/reports/{report_id}/results?status=incidents|changes|all|failed|broken|passed` - результаты тестов отчета из его Allure-данных (по умолчанию только failed и broken). Каждый результат сравнивается с предыдущим запуском теста в истории (`change`: `new_failure` / `still_failing` / `fixed` / `new_test`, `previous`), счетчики — в `changes`; `status=changes` оставляет новые падения и починенные тесты

## History API
- `GET /api/history` - скачать текущий `history.jsonl`
- `POST /api/history` - загрузить новый `history.jsonl`
- `GET /api/history/info` - получить метаданные `history.jsonl`
- `GET /api/history/dashboard` - получить агрегаты dashboard без скачивания всего файла
- `GET /api/history/dashboard/tests/{test_key}` - получить детали выбранного теста для dashboard
- `GET /api/history/runs?search=&status=&limit=&offset=` - постраничный список прогонов из history index
- `GET /api/history/runs/{run_uuid}/results?status=incidents|changes|all|...` - результаты тестов прогона со сравнением с предыдущим запуском
- `POST /api/history/rebuild-index` - принудительно полностью перечитать `history.jsonl` и пересобрать `history_index.json`

## Coverage API
- `GET /api/coverage` - список измерений покрытия
- `POST /api/coverage` - новое измерение (`multipart/form-data`): `kind` (`rest` | `graphql`), `spec` (файл `openapi.json` или схема GraphQL — SDL или JSON интроспекции), `report_ids` (ID отчетов через запятую), `name`, для REST — `base_path` и `host` (необязательный фильтр, несколько через запятую), для GraphQL — `endpoint`
- `GET /api/coverage/{id}` - результат измерения
- `POST /api/coverage/{id}/recalculate` - пересчитать с сохраненной спецификацией и теми же отчетами
- `DELETE /api/coverage/{id}` - удалить измерение

Как считается покрытие:
- Источник — текстовые log-вложения тестов в загруженных отчетах (`data/attachments/*.txt`), записи `api_controller`: `Запрос: METHOD URL`, `Статус код ответа: NNN`, `Запрос: "URL" <graphql-запрос> Переменные: ...`
- REST: вызов сопоставляется с шаблоном пути из спецификации с учетом base path. Хост из `servers` не используется как фильтр (генераторы часто пишут туда адрес, откуда скачали спецификацию). Если хост не задан, сервису принадлежат хосты, у которых хотя бы один запрос совпал с операцией; остальные хосты показываются отдельно
- GraphQL: запросы проверяются по схеме через `graphql-core`, учитываются поля, аргументы, фрагменты и union
- Измерение хранится снимком в `storage/coverage/<id>/` (спецификация, параметры и результат) и не меняется при загрузке новых отчетов

## Интеграция с Jira
Баги заводятся в Jira Server / Data Center 9.x из упавших тестов загруженного отчёта.
Все запросы в Jira делает backend от имени одного сервисного аккаунта по его Personal Access Token:
пользователям TestReport Storage не нужен доступ к Jira, а токен не попадает в браузер.

### Что умеет
- **Где создать баг**: кнопка «Создать баг» в шапке отчёта (тест выбирается в окне) или иконка бага в строке упавшего теста на вкладке «Результаты» (тест уже выбран). Иконка подсвечена у новых падений
- **Шаги воспроизведения** берутся из Allure по порядку и делятся на «Подготовку» (`setup`), «Тест» и «Завершение» (`teardown`). По умолчанию выбран «путь до падения»: шаги верхнего уровня без пропущенных и цепочка шагов до упавшего; подготовка и завершение выключены, если тест упал не в них. Наборы «Путь до падения», «Все», «Снять все», и любой шаг — галочкой
- **Повторы не засоряют задачу**: подряд идущие шаги с одинаковым именем (ретраи, ожидания статуса) сворачиваются в группу попыток, по умолчанию в задачу идёт последняя. Если упал сам шаг ожидания (таймаут), берётся последний опрос — видно, что ответил сервис. Повторы того же шага в других местах сценария остаются отдельными шагами
- **Запросы**: у шага показывается его запрос (`POST /api/v1/orders → 201`), в описание попадают запросы выбранных шагов, тело запроса и ответ, на которых упал тест. Режимы лога: «Запросы шагов», «Полный лог» (обрезается с начала, если не влезает в лимит Jira 32 000 символов), «Без лога»
- **Вложения**: логи и скриншоты теста приложены по умолчанию, дамп упавшего запроса — по желанию; лимит размера — `JIRA_MAX_ATTACHMENT_MB`
- **Стенд** — самый частый хост запросов теста без порта: сервисы одного стенда отличаются только портами (`host:4001`, `host:18081` → `http://host`). Название стенда можно задать в `JIRA_STAND_NAMES`
- **Автор теста** — `User` из `widgets/variables.json` отчёта; предлагается исполнителем, если такой пользователь есть в Jira
- **Поля задачи**: заголовок (`[Автотест] Тест: Тип ошибки — сообщение`, можно изменить), приоритет и компоненты из настроек проекта, метки (`JIRA_DEFAULT_LABELS` + теги теста), поле Environment (стенд и прогон). Ожидаемый результат обязателен — его пишет человек
- **Предпросмотр** описания и вкладка «Разметка Jira» с тем текстом, который уйдёт в задачу
- **Маскировка**: перед отправкой из логов и дампов убираются заголовки авторизации, Bearer-токены, JWT, значения ключей `password`, `token`, `secret`, `api_key` и других (свои ключи — в `JIRA_MASK_KEYS`)
- **Дубли**: задача связывается с падением по паре «тест + сигнатура ошибки» (`storage/jira/links.json`). Чип с ключом и статусом из Jira виден в строке теста — и в следующих отчётах, где этот тест падает так же. При создании бага окно предупреждает, если задача на это падение уже есть, или если похожая задача заведена по другому тесту с той же ошибкой; повторное падение можно добавить в неё комментарием

### Что нужно от автотестов
Интеграция работает с отчётами Allure 3 и берёт данные из них, без изменений в тестах, если они уже пишут:
- **Шаги** Allure (`allure.step`) — из них собираются шаги воспроизведения
- **JSON-вложение шага с запросом и ответом** — из него берутся запрос шага, стенд и тело упавшего запроса:
  ```json
  {
    "request_line": "POST http://stand.company.ru:4001/api/v1/orders",
    "request_body": {"sku": "SKU-1"},
    "response_status_code": 201,
    "response_body": {"id": 1}
  }
  ```
  Без таких вложений шаги всё равно попадут в задачу, а стенд определится по URL в текстовом логе
- **Переменная `User`** в `widgets/variables.json` (в Allure 3 задаётся через `variables` в конфиге отчёта) — автор теста
- **Текстовый лог** теста (`.txt` / `.log`) — для вложения и режима «Полный лог»

### Настройка
1. **Сервисный аккаунт.** Заведите в Jira пользователя для автотестов (например, `svc-autotest`) и дайте ему в целевом проекте права:
   - *Browse Projects*, *Create Issues*, *Create Attachments*, *Add Comments* — обязательно
   - *Assign Issues* — чтобы назначать исполнителя; сами исполнители должны иметь *Assignable User*
   - глобальное *Browse users and groups* — чтобы проверять, что автор теста есть в Jira (без него исполнитель подставляется без проверки)
2. **Personal Access Token.** Войдите под сервисным аккаунтом → профиль → *Personal Access Tokens* → *Create token*. Срок действия выбирайте с запасом и запишите дату: после истечения Jira начнёт отвечать 401
3. **Тип задачи.** Убедитесь, что в проекте есть тип `Bug` (или задайте свой в `JIRA_ISSUE_TYPE`) и что на экране создания нет обязательных полей кроме заголовка, приоритета, компонентов, меток, исполнителя и Environment — их форма заполнить не сможет
4. **Переменные окружения.** Для `docker compose` положите их в `.env` рядом с `docker-compose.yml` (файл в `.gitignore`):
   ```bash
   JIRA_BASE_URL=https://jira.company.ru
   JIRA_TOKEN=<personal access token>
   JIRA_PROJECT_KEY=CLM
   APP_PUBLIC_URL=https://test-reports.company.ru
   # по необходимости
   JIRA_STAND_NAMES=244.lnsk.infra.innoseti.ru=stage
   JIRA_DEFAULT_LABELS=autotest
   ```
   `APP_PUBLIC_URL` — адрес TestReport Storage, по нему в задаче появляются ссылки на отчёт и на тест в Allure. Полный список переменных — в разделе [Конфигурация](#конфигурация)
5. **Сертификат Jira.** Если у Jira сертификат внутреннего CA, смонтируйте его в контейнер и укажите путь в `JIRA_CA_BUNDLE`:
   ```yaml
   # docker-compose.override.yml
   services:
     backend:
       volumes:
         - ./certs/company-ca.pem:/app/certs/company-ca.pem:ro
   ```
   и `JIRA_CA_BUNDLE=/app/certs/company-ca.pem` в `.env`. `JIRA_VERIFY_SSL=false` отключает проверку целиком — только для тестовых стендов
6. **Перезапуск и проверка.** `docker compose up -d`, затем:
   ```bash
   curl http://localhost:8080/api/jira/config   # "enabled": true
   curl http://localhost:8080/api/jira/meta     # тип задачи, приоритеты, компоненты проекта
   ```
   `meta.unsupportedRequired` перечисляет обязательные поля проекта, которых нет в форме — если список не пустой, Jira будет отклонять задачи (см. шаг 3)
7. **Первый баг.** Откройте отчёт с падениями → «Результаты» → иконка бага у теста → заполните ожидаемый результат → «Создать баг». После создания в строке теста появится чип задачи

Без настроенной Jira кнопки остаются: черновик и предпросмотр работают, а создание задачи сообщает, каких переменных не хватает.

### Если что-то не работает
- **«Jira отклонила токен»** — токен неверный, отозван или истёк: выпустите новый (шаг 2)
- **«Сервисному аккаунту не хватает прав»** — проверьте права в проекте (шаг 1)
- **«Jira: <поле>: …»** при создании — проект требует поле, которого нет в форме, или значение не подходит экрану создания: смотрите `unsupportedRequired` в `/api/jira/meta`
- **«В проекте нет типа задачи …»** — поправьте `JIRA_ISSUE_TYPE` под название типа в проекте
- **«Jira недоступна: ConnectError / ConnectTimeout»** — backend не достаёт до `JIRA_BASE_URL`: проверьте сеть контейнера, прокси и `JIRA_TIMEOUT_SECONDS`
- **Ошибка сертификата** — задайте `JIRA_CA_BUNDLE` (шаг 5)
- **Исполнитель не подставляется** — логина из `User` в отчёте нет в Jira или у аккаунта нет *Browse users and groups*; исполнителя можно вписать вручную
- **Стенд определился не тот** — в тесте больше запросов к стороннему сервису, чем к стенду: стенд выбирается по большинству запросов, проверьте `request_line` во вложениях шагов
- **Нет статуса в чипе задачи** — задача удалена или перенесена, либо Jira временно недоступна; ключ остаётся, статус подтянется при следующем открытии отчёта

## Jira API
- `GET /api/jira/config` - включена ли интеграция, адрес Jira, проект
- `GET /api/jira/meta` - тип задачи, приоритеты и компоненты проекта (из createmeta, кэш 10 минут)
- `GET /api/jira/draft?report_id=&test_id=` - черновик бага по тесту: шаги по секциям, стенд, автор, вложения, предлагаемые заголовок и метки, уже заведённые задачи
- `POST /api/jira/preview` - описание задачи в разметке Jira для выбранных шагов и режима лога
- `POST /api/jira/issues` - создать баг: задача, вложения, связь с падением
- `POST /api/jira/issues/{key}/comments` - добавить повторное падение комментарием в существующую задачу
- `GET /api/jira/links?report_id=` - заведённые задачи по тестам отчёта со статусами из Jira

Порядок подключения и устройство — в разделе [Интеграция с Jira](#интеграция-с-jira).

## Интерфейс
Адреса страниц (`http://localhost:9999` в Docker-развертывании или `http://localhost:5173` в dev-режиме):
- `/dashboard` - дашборд качества
- `/reports`, `/reports/{id}` - загруженные отчеты
- `/runs`, `/runs/{uuid}` - прогоны из истории
- `/coverage`, `/coverage/new`, `/coverage/{id}` - измерения покрытия API

Что показывает Dashboard:
- KPI: pass rate с риском, прогоны, уникальные тесты, нестабильные тесты, P95 длительности
- Тренд последних прогонов по статусам `passed / failed / broken`; клик открывает отчет или прогон
- Общая стабильность: распределение статусов и списки «всегда проходят», «всегда падают», «инциденты»
- Самые нестабильные тесты (есть и успешные, и упавшие запуски) с полосой последних 10 статусов
- Топ сигнатур падений и состояние по тегам; клик включает соответствующий фильтр
- Проблемные прогоны по загруженным отчетам

Как используются данные:
- Summary и результаты тестов отчета берутся из распакованных Allure-отчетов
- QA-метрики, тренды и прогоны строятся по агрегированному индексу `storage/history_index.json`
- `history_index.json` создается лениво при первой обработке `history.jsonl` и не требуется для старта сервиса
- При загрузке нового `history.jsonl`, если файл дописан в конец, backend обычно дочитывает только новый хвост и обновляет индекс инкрементально
- Если индекс отсутствует, поврежден или есть сомнение в консистентности, можно вызвать `POST /api/history/rebuild-index` для полного rebuild из текущего `history.jsonl`
- Если `history.jsonl` не загружен, history-based виджеты показывают пустое состояние

## Конфигурация
Переменные окружения backend:
- `APP_STORAGE_ROOT` - путь к директории хранения (по умолчанию: `storage`)
- `APP_MAX_REPORTS` - максимальное количество хранимых отчетов (по умолчанию: `10`)
- `APP_MAX_UPLOAD_SIZE_MB` - максимальный размер загружаемого ZIP (по умолчанию: `512`)
- `APP_HISTORY_MAX_FILE_SIZE_MB` - максимальный размер `history.jsonl` (по умолчанию: `100`)
- `APP_MAX_INDEXED_RUNS` - сколько последних прогонов держать в индексе истории (по умолчанию: `1000`)
- `APP_CORS_ORIGINS` - разрешенные origin через запятую, если UI и backend на разных хостах

Интеграция с Jira (Server / Data Center 9.x, задачи создаются от сервисного аккаунта):
- `JIRA_BASE_URL` - адрес Jira, например `https://jira.company.ru`
- `JIRA_TOKEN` - Personal Access Token сервисного аккаунта
- `JIRA_PROJECT_KEY` - проект, в котором создаются баги
- `JIRA_ISSUE_TYPE` - тип задачи (по умолчанию: `Bug`)
- `JIRA_DEFAULT_LABELS` - метки каждой задачи через запятую (по умолчанию: `autotest`)
- `JIRA_VERIFY_SSL` - `false`, чтобы не проверять сертификат Jira; `JIRA_CA_BUNDLE` - путь к своему CA
- `JIRA_MAX_ATTACHMENT_MB` - максимальный размер вложения (по умолчанию: `10`)
- `JIRA_STAND_NAMES` - названия стендов по хосту: `host=stage,host2=dev`
- `JIRA_MASK_KEYS` - дополнительные ключи, значения которых маскируются, через запятую
- `JIRA_TIMEOUT_SECONDS` - таймаут запросов к Jira (по умолчанию: `20`)
- `APP_PUBLIC_URL` - адрес TestReport Storage для ссылок из задачи на отчёт и тест в Allure

Поведение ротации:
- После загрузки нового отчета, если общее количество превышает `APP_MAX_REPORTS`,
  автоматически удаляются самые старые директории отчетов.
